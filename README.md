# LiteGameNext

LiteGame 客户端的**重写工程**：服务端与共享判定/协议/同步包沿用旧仓，只重写客户端。

| 项 | 值 |
|---|---|
| 引擎 | Unity 2022.3.55f1c1（URP 14.0.11） |
| 形态 | 单机可玩 + 联机射击（服务端权威、客户端预测和解） |
| 旧工程 | `E:\unityProject\Test`（服务端、`com.litegame.{sim,net,sync}` 包、Luban 表源、云侧部署脚本的唯一来源） |
| 当前状态 | **只有设计文档，代码未开工**（进度见 [Docs/进度/迁移进度.md](Docs/进度/迁移进度.md)） |

## 为什么重开

旧工程客户端自研代码 71,895 行（framework 25,296 + 业务 46,599）、79 个程序集、186 个接口、237 篇文档、3 套代码生成、C#/Lua 双实现。这不是"某个文件写得差"，而是**框架规模超过了游戏规模**。

新工程要证明相反的事：**一个人一个下午能读完、一天能跑通**。用硬预算（运行时代码 ≤ 25k 行、程序集 ≤ 5 个、接口 ≤ 20 个、文档 ≤ 8 篇）替代"用更多机制解决机制带来的问题"。

## 三条不可协商的约束

1. **共享包只读**：`com.litegame.sim` / `com.litegame.net` / `com.litegame.sync` 原样消费。改了它们等于改服务端协议与确定性判定，必须回旧仓走 `toolbox.py build-hash` 流程。
2. **一个功能只在一侧实现**：C# 负责引擎与性能敏感路径，Lua 负责页面逻辑与可热更数据；同一功能不得两边各写一份。
3. **预算超限即停手**：加程序集、加接口、加机制之前，先看 01 §11 的预算表与 §12 的反清单；超了先减再加。

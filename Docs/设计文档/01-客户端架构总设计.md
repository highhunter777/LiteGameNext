## 1. 目标与非目标

### 1.1 目标（每条都可验收）

| # | 目标 | 验收方式 |
|---|---|---|
| G1 | **可读完**：运行时业务代码 ≤ 25,000 行、程序集 5 个、接口 ≤ 20 个 | `Tools/verify.py --budget` 机检 |
| G2 | **可跑通**：空工程到能操控角色进一局 ≤ 一个阶段（04 的 P0/P1） | 阶段退出条件 |
| G3 | **可改**：改一个页面/一个功能只动 1~3 个文件，不需要理解框架 | 评审时抽查 5 个改动 |
| G4 | **可测**：纯逻辑（判定对拍、和解、配置摘要）在 dotnet 里秒级可测，不依赖 Unity | `dotnet test` |
| G5 | **可热更**：Lua 页面 + 配置 + 资源包可整包替换，不重装客户端 | 04 P3 退出条件 |

### 1.2 非目标（写了就是为了不做）

- 不做通用客户端框架，不做对外 SDK，不服务"第二个游戏"。
- 不做 ECS、不做多后端渲染抽象、不做跨平台 UI 方案矩阵（Windows 优先，Android 次之，其余不支持）。
- 不自研 DI 容器 / 模块系统 / 作用域 / 事务化热更 / UI 绑定代码生成。
- 不重写服务端、判定、协议（只消费）。

## 3. 分层与依赖规则

```
┌────────────────────────────────────────────────────────────┐
│ Presentation  Ui(ScreenManager/Screen) · Battle 表现        │ L3 ┐
│               (角色/武器/相机/HUD/命中反馈)                  │    │ 热更候选
├────────────────────────────────────────────────────────────┤    │ Game
│ Feature       Launch · Online · Battle · Settings            │ L2 ┘
├────────────────────────────────────────────────────────────┤
│ Core          Log · Time · Events · Assets · Config · Lua  │ L1 ┐
│               Http · Storage · Host(宿主壳 GameEntry/BootEntry)│   │ AOT
├────────────────────────────────────────────────────────────┤    │ Core
│ Shared        com.litegame.{sim,net,sync}（只读）            │ L0 ┘
└────────────────────────────────────────────────────────────┘
```

**规则**（违反即评审不通过；R1/R2/R7 可机检）：

- **R1 依赖只向下**：L3→L2→L1→L0。同层内允许横向调用，但只能经构造参数拿到对方实例，禁止静态单例互取。
- **R2 Core 不认识 Game**：`LiteGame.Core.asmdef` 不引用 `LiteGame.Game`，由程序集强制。
- **R3 Feature 之间不互 new**：跨 Feature 通信只有两条路——构造时传入对方实例，或经 Core 的 `EventBus` 发一个强类型事件。禁止 Feature A 直接读 Feature B 的内部字段/集合。
- **R4 接口只在三种情况出现**：① 有第二个实现；② 需要测试替身（IO/时间/网络）；③ 跨程序集边界。其余一律用具体类。全仓接口预算 ≤ 20。
- **R5 共享包只读**：`Packages/com.litegame.*` 三个包不在本工程内修改。需要改 = 回旧仓改 + 重算 BuildHash（04 §7）。
- **R6 一个功能只在一侧**：见 03 §1；跨边界调用只走 `Bridge`，且只传原始类型。
- **R7 AOT 不引用热更面**：`LiteGame.Core`（连同共享包）是 AOT 侧，`LiteGame.Game` 是未来热更侧。AOT 侧**不得出现任何 Game 类型**（含 `using`、泛型参数、特性实参）；启动只能经 `BootEntry.Factory` 一个缝（§4、§15）。这条是 HybridCLR 的硬约束，今天就按它写，未来接 HybridCLR 不需要改结构。

**为什么不用 79 个程序集**：程序集的价值是"编译隔离 + 依赖强制"。本工程只有三个真实的隔离需求（Core↔Game 单向即 AOT↔热更、Editor、测试），其余程序集只带来编译碎片与 asmdef 维护成本。拆分门槛见 02 §1。

## 4. 启动链（三件套）

```csharp
// Core/Host/IGame.cs —— AOT 侧认识的唯一业务抽象（R4 的"跨程序集边界"接口）
public interface IGame : IDisposable
{
    UniTask StartAsync();
    void Tick(float dt);
}
```

```csharp
// Core/Host/GameEntry.cs —— AOT 宿主壳：唯一 MonoBehaviour 入口（DefaultExecutionOrder(-1000)，DontDestroyOnLoad）
// 只认 IGame，不认识任何业务类型——这样 Game 程序集将来能整体变成热更程序集（§15）
public sealed class GameEntry : MonoBehaviour
{
    private IGame _game;
    private void Awake()   => _game = BootEntry.Create(this, LaunchConfig.Load()); // 工厂由 Game 侧注册
    private void Start()   => _game.StartAsync().Forget(Log.Error);               // 进 Boot 态
    private void Update()  => _game.Tick(Time.unscaledDeltaTime);
    private void OnDestroy() => _game?.Dispose();
}
```

```csharp
// Core/Host/BootEntry.cs —— AOT → 热更 的唯一缝：一个静态工厂，一次注册
public static class BootEntry
{
    public static Func<GameEntry, LaunchConfig, IGame> Factory;

    public static IGame Create(GameEntry entry, LaunchConfig cfg)
        => Factory?.Invoke(entry, cfg)
           ?? throw new InvalidOperationException("业务程序集未注册：GameBootstrap 未执行");
}
```

```csharp
// Game/Boot/GameBootstrap.cs —— 业务侧唯一自注册点（HybridCLR 下等于热更程序集装载后的入口）
public static class GameBootstrap
{
    [RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.BeforeSceneLoad)]
    private static void Register() => BootEntry.Factory = static (entry, cfg) => Game.Build(entry, cfg);
}
```

```csharp
// Game/Boot/Game.cs —— 全工程唯一 new 业务件的地方（组合根）；没有容器、没有反射、没有特性
public sealed class Game : IGame
{
    public readonly Log Log;
    public readonly AssetHost Assets;
    public readonly ConfigHost Config;
    public readonly LuaHost Lua;
    public readonly UiHost Ui;
    public readonly AccountApi Account;    // HTTP：登录 / 票据 / 战绩
    public readonly LobbyApi Lobby;        // HTTP：房间列表 / 创建 / 进出
    public readonly RoomFeature Room;      // RoomClient：连接 / 进房 / 席位 / 重连
    public readonly SettingsService Settings;
    public readonly BattleFeature Battle;
    public readonly AppFlow Flow;

    public static Game Build(GameEntry entry, LaunchConfig cfg)
    {
        var log      = new Log(cfg.LogLevel, entry.transform);
        var assets   = new AssetHost(cfg.AssetMode, cfg.CdnRoot, log);
        var config   = new ConfigHost(assets, log);
        var lua      = new LuaHost(assets, log);
        var ui       = new UiHost(assets, lua, entry.transform);
        var settings = new SettingsService(log);
        var account  = new AccountApi(cfg.MetaUrl, log);                  // 持有 AccountSession（票/账号事实）
        var lobby    = new LobbyApi(cfg.MetaUrl, account.Session, log);
        var room     = new RoomFeature(account.Session, log);             // 唯一持有 RoomClient 的件
        var battle   = new BattleFeature(room, assets, config, lua, log); // 只消费 Room 的事实与快照
        return new Game(log, assets, config, lua, ui, account, lobby, room, settings, battle);
    }

    // StartAsync（进 Boot 态）/ Tick（§5 五步）/ Dispose（§4 逆序）按 §5、§6 展开，此处省略
}
```

| 阶段 | 做什么 | 失败去向 |
|---|---|---|
| `Awake` | `BootEntry.Create` → `Game.Build`：创建 Core 与 Feature 实例，不加载资源、不发网络 | 错误屏（`BootstrapErrorPresenter`，AOT 侧一个文件） |
| `Start` | `AppFlow.EnterAsync(Boot)`：初始化内容包 → 装载配置 → 启动 Lua → 进首屏 | 错误屏 + 日志；可重试一次 |
| `Update` | `Tick(dt)`：固定 5 步（§5） | 单步异常 → 记录并停用该 Feature，不整机崩溃 |
| `Dispose` | 逆序释放：Flow → Battle → Room → Lobby → Account → Ui → Lua → Config → Assets → Log | 幂等 |

**为什么要多一层 `BootEntry`**：HybridCLR 要求 AOT 程序集不引用热更程序集，而"谁创建组合根"天然是 AOT→Game 的引用。用一个静态工厂把这次引用反转成 Game→Core 的注册，代价是 15 行，换掉未来"把启动链搬家 + 改场景引用"的返工。

**约束**：组合根文件 ≤ 200 行；出现第 3 段"装配钩子"就说明该拆 Feature 了，而不是引入容器。

## 5. 帧循环与 tick 序

`Game.Tick(dt)` 里**固定顺序**调用，顺序是设计的一部分，写在 `Game.cs` 一处：

| 序 | 调用 | 责任 | 预算 |
|---|---|---|---|
| 1 | `InputSampler.Sample(dt)` | 采样本机输入 → 意图帧（仅本机是玩家时） | < 0.2 ms |
| 2 | `Room.Tick()` | `RoomClient.TickIncoming()` / `TickOutgoing()`；派发 `StartGame`/`Snapshot`/`Seats`/`MatchEnded` | < 0.3 ms |
| 3 | `Battle.Tick(dt)` | 定步长累加 → 本地预测 → 快照和解 → 表现插值 → HUD | < 6 ms |
| 4 | `Ui.Tick(dt)` | 前台页 `OnUpdate`（自带节拍闸，默认 10 Hz） | < 0.5 ms |
| 5 | `Dev.Tick()` | F1 面板、弱网开关（发布包不存在） | 调试期 |

**纪律**：

- 逻辑帧 60 Hz，由 `FixedStep` 累加器驱动；表现层用 `dt` 插值，**不得**把逻辑写进 `Update`。
- 战斗稳态 **GC 0 B/帧**：不 new 集合、不装箱、不 `foreach` 接口集合（用索引循环）、字符串只在页面打开时拼。
- 一次 tick 只允许一个 Feature 拥有"权威状态"；别名（两份可变状态）是 bug 温床，禁止 Mirror/Shadow 式副本（旧战斗侧 `BattleSnapshotMirror` 这类结构不再出现）。

## 6. 应用状态机

**形态**：一个 `enum` + 一个 `IAppState` 接口 + 每状态一个文件。不引入泛型状态机、阶段图、捕获回放、转移表。

```csharp
public enum AppState { Boot, Patch, Login, Lobby, Room, Battle, Result, Error }

public interface IAppState
{
    UniTask EnterAsync(object args);   // args 用具体 record/class，不用 object 泛型袋
    UniTask ExitAsync();
}
```

| 状态 | 进入条件 | 主要动作 | 失败/退出 |
|---|---|---|---|
| `Boot` | 进程启动 | 初始化内容包、装载配置、启动 Lua、显示首屏 | 失败 → `Error` |
| `Patch` | 有版本策略 | 版本检查 → 下载 → 摘要校验 → 激活 → 重进 `Boot` | 取消 → `Lobby`（用旧内容） |
| `Login` | 无有效票据 | 账号登录（`AccountApi`）→ 存票 | 失败留在本态并可重试 |
| `Lobby` | 有票 | 房间列表轮询、创房/快速进入、打开设置/战绩 | 掉线 → `Login` |
| `Room` | 已进房 | 席位/房主/开始对局；等 `StartGame` | 离开/被踢 → `Lobby` |
| `Battle` | 收到 `StartGame` | 连接、输入、预测和解、结算数据 | 结束 → `Result`；断线 → 重连或 `Lobby` |
| `Result` | 收到 `MatchEnded` | 结算展示 → 回 `Lobby` | — |
| `Error` | 任意致命错误 | 展示错误 + 返回 `Boot`/退出 | — |

**约束**：状态之间不互相持有；切换只经 `AppFlow.EnterAsync(state, args)`，且 `AppFlow` 是唯一写者（页面自己不得切状态，只能发请求）。

## 7. UI 架构

### 7.1 结构

```
UIRoot (DontDestroyOnLoad, 一个预制体)
├─ Canvas_Screen   页面（全屏，单栈顶）
├─ Canvas_Popup    模态 / Toast
└─ Canvas_Overlay  转场遮罩 / Loading
```

- **`ScreenManager`** 唯一 API：`ShowAsync(id, args)` / `ReplaceAsync(id, args)` / `BackAsync()` / `CloseAllAsync()`。栈深 ≤ 4。
- **一个页面 = 一个预制体 + 一个 `UiBinder` + 二选一的逻辑件**：
  - C# 逻辑页：`ScreenBase` 子类（`OnShow/OnHide/OnUpdate` 三个虚方法）。
  - Lua 逻辑页：挂 `LuaScreen`，`script = "UI.Page_Lobby"`，逻辑全在 Lua（03 §4）。
- **`UiBinder`**：Inspector 里一个数组 `{ key, Component }`，替代旧工程 11,181 行的绑定生成/校验/预览/工作台。key 就是子节点名（与旧约定一致，旧页面零改动）。
- **页面目录**：`ScreenId`（enum）+ `ScreenCatalog`（`ScreenId → 预制体地址`），一个文件两屏。找不到地址 = 编译期就该发现，不在运行期反射。

### 7.2 约定

- **单写者**：只有 `ScreenManager` 能开/关页面；Lua 侧只有 `Bridge.ui` 能调它。
- **三态**：每个数据页必须有 `Loading / Empty / Error` 三态文案键，不允许白屏（旧工程踩过的坑）。
- **预载**：进入 `Lobby`/`Battle` 前各自预载本态所需预制体；不做全局资源常驻。
- **焦点**：模态打开 → `InputSampler` 暂停游戏意图（一个 `IsModalOpen` 布尔，不做拦截器链）。

## 8. 内容与配置

### 8.1 资源（YooAsset 3.0.5）

`AssetHost` 只有四个能力：

| 方法 | 说明 |
|---|---|
| `InitAsync()` | 初始化 `Main` 包（编辑器模拟模式 / 离线 / 联机三选一由 `LaunchConfig.AssetMode` 决定） |
| `CheckAndUpdateAsync(progress)` | 版本请求 + 下载 + 进度回调；返回是否需要重启流程 |
| `LoadAsync<T>(location)` | 返回 `AssetHandle<T>`，释放即 `Dispose` |
| `VerifyDigestAsync()` | 包摘要与签名校验（Lua 包与配置包各一份） |

**不做**：租约（lease）、代次（generation）、共享加载树、10 阶段事务。缓存只有一层 `Dictionary<location, entry>`，随包切换整体清空。

### 8.2 配置（Luban）

- 表源在旧仓 `Luban/Data`（单源），生成物两处：C# 表类 → `Assets/GameData/Generated`，Lua 表 → `Assets/Scripts/Lua/cfg`。
- 运行期：`ConfigHost.LoadAsync()` 读 `.bytes` → `cfg.Tables`；Lua 侧经 `Bridge.data` 读同一份表的投影（不重复解析）。
- **`ConfigDigest` 必须与旧客户端逐字节一致**：服务端用 `StartGame.ConfigHash` 校验，摘要算法照搬旧仓 `ConfigService.GameplayDigestBase`，不重设计（04 §4 有对拍用例）。

### 8.3 补丁流（`PatchSteps`，四步）

1. 请求版本清单 → 2. 比较本地清单 → 3. 下载差异 bundle + 校验摘要 → 4. 切换包根并重启内容（Lua 重载 + 配置重载 + 回 `Boot`）。

失败处理：任一步失败 → 保留旧内容继续进游戏（可玩），日志 + 设置页可见"内容版本"。

## 9. 战斗集成（与共享包的边界）

```
输入         InputSampler ──SimInputFrame──▶ RoomClient.SendInput(frame, input, viewFrame)
网络         RoomClient.TickIncoming() ──▶ StartGame / Snapshot / Seats / MatchEnded / ReconnectResponse
预测+和解    LocalPredictor：本地帧步进 Sim → 快照到达时回滚到快照帧并重放到当前帧
表现         BattleView：快照/预测态 → 角色/武器/相机/HUD/VFX/伤害数字（插值，不写逻辑）
```

- 共享包给的面（只读）：`RoomClient.Connect/SendJoin/SendStartMatchRequest/SendInput/TickIncoming/TickOutgoing/BeginReconnect/CompleteRestore/Disconnect/SendLeave`，事实属性 `PlayerId/IsOwner/MapId/ExpectedPlayers/StartGame/MatchResult/Seats/Phase`。
- **`RoomFeature` 是 `RoomClient` 的唯一持有者**（`Features/Online/RoomFeature.cs`）：负责连接、进房、席位、房主、重连相位；`BattleFeature` 只通过构造参数拿到它，不自己建连接。这样"房间会话"只有一份状态，`Room` 与 `Battle` 两个状态共用。
- 客户端**只做三件事**：采样输入、跑本地预测、把状态画出来。判定规则一律在 `com.litegame.sim` 内，客户端不得复制一份。
- 定步长：逻辑 60 Hz；`SendInput` 的 `viewFrame` 用于服务器回溯判定，取值口径照搬旧客户端（04 §2 第 13 行）。
- **一致性是最高风险**：`LocalPredictor`/`SimView` 的核心算法（预测帧推进、回滚重放、插值采样、静默门）按算法移植、不按结构移植，并用 digest 对拍（04 §4）。

### 9.3 动画：直接用 Animator，只包一层

**决策**：不自研动画系统。旧工程为此写了 2,287 行（`Services/Animation` 30 文件 1,464 行 + `Adapters/Unity/AnimationBackends` 7 文件 823 行：后端抽象、Profile 配置、帧驱动采样、混合调度）。新工程直接用 Unity Mecanim，只加一层 ≤ 250 行的薄封装。

**分工**（边界就是"谁持有状态机"）：

| 层 | 归属 | 内容 |
|---|---|---|
| 状态机 / 混合 / 过渡 / 层 / 事件 | **AnimatorController 资产（美术）** | Locomotion 混合树、UpperBody 层（瞄准/开火）、过渡条件、Animation Event |
| 参数契约 | **`AnimationIds.cs`**（程序，≤ 60 行/角色型） | `Animator.StringToHash` 常量：状态、参数、层；一个角色型一份 |
| 写参数 | **`CharacterAnimator.cs`**（≤ 150 行） | `Play(state, fade)`、`SetFloat/Bool/Trigger(hash, value)`、`SetLayerWeight`；**不判断该不该切** |
| 推导参数 | **`CharacterView`** | 从 sim 状态算速度/落地/瞄准/开火，变值才写 |

**五条纪律**：

1. **动画不参与判定**：`applyRootMotion = false`；位置与朝向一律来自 sim，视图只跟随。需要位移类技能时把位移烘成 sim 表（复用地图烘焙管线），**不让 Animator 推角色**。
2. **状态机只有一份**：Animator 里那个就是唯一状态机；代码里禁止再写动画 FSM、状态优先级表、队列。
3. **参数名不散落**：调用点只出现 `AnimationIds.Speed` 这类 int 常量，禁字符串字面量。新增参数 = 改一处常量 + 美术在 Controller 加同名参数（这一行就是程序-美术契约）。
4. **事件走 Unity 原生**：Animation Event 直接调同 GameObject 上 `CharacterView` 的方法；不接全局事件总线、不做动画事件表。
5. **无每帧分配**：参数只在变值时写（`CharacterView` 缓存上次值）；不在 `Update` 里查组件、拼字符串、用 LINQ。

**明确不做**：后端抽象（Animator/Playables 二选一已定）、动画 Profile 配置系统、帧驱动采样器、运行时 RootMotion 目录（旧 `RootMotionCatalog` 仅在战斗确实需要位移数据时以烘焙表形式回归）。

**以后需要程序化动画**（IK、上半身叠加）时：先用 Animator 的 IK Pass，再评估 Playables——不预先抽象。

**代价**：失去"换后端"能力（本来不需要）；状态机维护归美术（本来也是）；程序只保证参数契约与写入纪律。

#### 9.3.1 参数契约（已定）

| 参数 | 类型 | 写入方 | 用途 |
|---|---|---|---|
| `Speed` | float | `CharacterView` | 插值后的水平速度（m/s），混合树用 |
| `Grounded` | bool | `CharacterView` | 是否落地 |
| `Aiming` | bool | `CharacterView` | 越肩瞄准态 |
| `Fire` | Trigger | `CharacterView` | 开火（单次） |
| `Reload` | Trigger | `CharacterView` | 换弹开始 |
| `Death` | Trigger | `CharacterView` | 死亡（切死亡态 / 布娃娃开关） |
| `UpperBody` | 层（int = 1） | `CharacterAnimator.SetLayerWeight` | 瞄准/开火叠加层 |

**规则**：① 只增不改——改名要程序与美术同时改，并落在 `AnimationIds` 的同一次提交里；② 参数只由 `CharacterView` 写，其他代码不得直接持有 `Animator`；③ 其余动作（换枪、翻滚、受击）等 P1 有真实需求再进契约，不预留空参数。

`AnimationIds.cs` 随 P1 的 `Battle/View` 一起落地，不在 P0。

## 12. 反清单（明确不做）

1. 不自研 DI 容器、ServiceContainer、Scope、Module/Segment 装配系统。

### 12.2 工程与流程

12. 不为"将来可能"预留参数、回调、扩展点；需要时再改（改比猜便宜）。

### 12.3 内容

## 14. 架构模式选型（主流模式，最小实现）

原则：**模式只用来命名已经存在的东西**，不为了"用模式"加机制。每个模式只有一个落点、一个行数预算；找不到消费者的模式一律不引入。

| 模式 | 主流叫法 | 本工程落点 | 最小实现 | 明确不做 |
|---|---|---|---|---|
| 分层 | Layered / Clean-lite | L0–L3（§3） | 4 层、单向依赖 | 不做 DTO 逐层转换、不做领域层隔离仪式 |
| 端口与适配器 | Ports & Adapters | `Core/Assets`、`Core/Http`、`Core/Timing` 的 3 个接口 + 实现 | 接口只因"测试替身"存在（R4） | 不做 `Adapters/` 目录、不做全量抽象 |
| 组合根 | Composition Root | `Game.Build` | 一个方法、一处 `new` | 不做 DI 容器/特性扫描 |
| 状态 | State | `AppFlow` + `IAppState` | enum + 每态一个类 | 不做转移表/子状态机/守卫链（旧 FSM 1,391 行） |
| 观察者 | Observer / Pub-Sub | `Core/Events` | 强类型 `Subscribe<T>`/`Publish<T>`，委托字典 | 不做反射事件总线、不跨线程派发 |
| 用例 | Use Case / Interactor | `Features/*` 的公开方法 | 普通类方法 | 不做 Command 对象 + Handler 体系 |
| MVP | Model-View-Presenter | View=预制体+MonoBehaviour；Presenter=`ScreenBase` 子类或 Lua 页；Model=Feature/Service | 单向：事件 → Presenter → Model → 刷新 View | 不做数据绑定框架、不做 MVVM 双向绑定 |
| 仓储 | Repository-lite | `LocalStore`（设置/票据/内容版本） | 一个键值门面 + 类型化读写 | 不做 UnitOfWork/聚合根 |
| 命令 | Command | 输入意图 `SimInputFrame`、`DevConsole` 指令 | 结构体/字符串表 | 不做命令总线、不做撤销栈 |
| 对象池 | Object Pool | 仅子弹与命中特效两处 | `Stack<T>` + 工厂委托（各 ≤ 60 行） | 不做通用池框架（旧 `Core/Pool` 541 行） |
| 特性模块 | Feature Module | `Features/<域>` | 一目录一域、构造注入 | 不做模块注册表/生命周期协议 |

**明确不采用**（并写清为什么不）：DDD 聚合/领域事件、CQRS/Event Sourcing、ECS/DOTS、GAS、行为树/GOAP、第三方 Unity MVC 框架（QFramework/ET/GameFramework 一类）、消息中间件、泛型依赖注入。

理由统一：当前只有一个客户端、一种玩法、一个人维护。上述模式在"多人多年多产品"时才回本，在现在是纯负债——旧工程 186 个接口、79 个程序集就是这些负债的账本。

## 15. HybridCLR 演进预留（现在只锁边界，不装包）

**目标**：未来把业务程序集 `LiteGame.Game` 变成热更程序集，实现"改 C# 逻辑不重装客户端"。本期**不安装 HybridCLR、不建热更程序集、不生成补充元数据**，只把边界锁死，使接入变成"装包 + 改 asmdef + 加装载步骤"，而不是重构。

### 15.1 今天就生效的四条（已落在 §3 R7 与 §4）

| # | 约束 | 落地物 | 机检 |
|---|---|---|---|
| H1 | AOT 侧（`LiteGame.Core` + 共享包）不出现任何 `LiteGame.Game` 类型 | `LiteGame.Core.asmdef` 不引用 Game；namespace 扫描 | `verify.py`：Core 源码里 `LiteGame.Game/Boot/Ui/Features` 出现 0 次 |
| H2 | 启动只经一个工厂缝，AOT 侧零反射 | `Core/Host/BootEntry.Factory` + `Game/Boot/GameBootstrap.Register` | 人工评审 + 上面的 namespace 扫描 |
| H3 | Game 只向下引用（Core / Unity / 共享包），不反向 | asmdef references | asmdef 检查 |
| H4 | 跨程序集边界只走 Core 里的接口（`IGame`、`IAssetHost`、`IHttp`、`IClock`） | 4 个接口（全仓接口预算 20 的一部分） | 评审 |

**为什么入口必须在 AOT**：HybridCLR 允许"热更 → AOT"的引用，不允许"AOT → 热更"的引用（编译期就要求 AOT 程序集不引用热更程序集）。如果 `GameEntry` 留在 Game 里，接入时就得把入口、场景引用、错误屏一起搬家——这是 P0 就要避开的返工。

### 15.2 接入时需要做的事（届时按 04 §8 判据执行）

1. 装 HybridCLR 包（版本与 Unity 2022.3.55f1c1 对齐），跑 `HybridCLR/Generate/All`。
2. `LiteGame.Game.asmdef` 从"普通程序集"改为"热更程序集"；`GameBootstrap.Register` 变成装载后调用。
3. 启动序列改为：AOT 启动 → 从内容包下载/校验热更 dll（复用 `AssetHost` 的摘要校验）→ `Assembly.Load` → `GameBootstrap.Register()` → `BootEntry.Create`。
4. 打包流水线加一步：编译热更 dll → 收进内容包的 `Code` 组 → 更新清单摘要。
5. 二次启动耗时目标 ≤ 300 ms（装载 + 元数据初始化）。

### 15.3 已知坑与规避（写在这里，避免接入时才发现）

| 坑 | 后果 | 本工程的规避 |
|---|---|---|
| 泛型值类型实例化缺元数据 | 运行期报 `AOT generic` 缺失 | 热更侧集合的泛型参数**优先用引用类型**；确需 struct 的登记进 `补充元数据清单`（一个文件，≤ 20 行） |
| 代码裁剪删掉被反射使用的 AOT 类型 | 运行期 `MissingMethod` | AOT 面只有 Core 八件，`link.xml` 白名单可控；ViewModel/协议类型不放热更侧 |
| 热更侧 MonoBehaviour 支持有限 | 视图挂不上/序列化异常 | **MonoBehaviour 一律留在 AOT 或场景**（`BattleView`/`HudView`/`LuaScreen` 属表现层，跟着预制体走）；热更侧只放纯 C# 逻辑 |
| 热更 dll 与 AOT 共享结构重复定义 | 类型不一致/序列化错位 | 协议与判定结构只在共享包（AOT）；热更侧不得重新定义 |
| 首次装载卡顿 | 启动变慢 | 装载与元数据初始化放在 `Patch/Boot` 的 Loading 段，不阻塞首帧 |

**代价评估**（接入前必须承认）：包体 +2~4 MB、启动 +100~300 ms、调试链路变复杂（需 `HybridCLR` 的调试符号方案）、出包步骤 +1。因此"未来可能"不等于"现在做"——只有在"必须不改安装包就修 C# 逻辑"成为真实需求时才接。

**与 Lua 的关系**：见 03 §11。两者是不同层级的热更（Lua = 页面逻辑/数值/文案，即时生效、免重启；HybridCLR = C# 逻辑，需装载、可重启），不冲突，也不互相替代。

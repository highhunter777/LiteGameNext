> **版本**：v0.2（2026-11-06）
> **定位**：把 01 的架构落到磁盘——程序集划分与 AOT/热更两面、完整目录树与每目录预算、命名与文件纪律、资源与场景、第三方清单、与旧仓共享输入的同步机制。

## 1. 程序集：5 个

| asmdef | 位置 | 职责 | 引用 | 为什么单独 |
|---|---|---|---|---|
| `LiteGame.Core` | `Assets/Scripts/Core` | 基础设施（AOT）：日志、时间、事件、资源、配置、Lua 宿主、HTTP、存储 + 宿主壳 `Boot/` | 引擎、UniTask、YooAsset、xLua、Newtonsoft、Luban 生成物 | 与业务解耦；AOT 侧，可被测试工程直接引用（01 R7） |
| `LiteGame.Game` | `Assets/Scripts/Game` | 业务（**未来热更程序集**）：Game 组合根、UI、Launch/Meta/Battle/Settings/Dev | `LiteGame.Core`、共享包 | 业务整体，不拆细；只向下引用 |
| `LiteGame.Editor` | `Assets/Scripts/Editor` | 构建、地图烘焙、GM 窗口 | 前两者 | 不随包发布 |
| `LiteGame.Tests.EditMode` | `Assets/Scripts/Tests/EditMode` | 编辑期用例 | 前两者 | Unity 测试程序集约定 |
| `LiteGame.Tests.PlayMode` | `Assets/Scripts/Tests/PlayMode` | 运行期用例 | 前两者 | 同上，需随 Player 编译 |

**拆分门槛**（不满足不拆）：① 目录内 > 300 个 .cs；② 全量编译 > 30 s 且瓶颈可定位到该程序集；③ 有真实独立发布需求（如工具 SDK）。三条都不满足时，**用目录与命名空间管理，不用程序集**。

旧工程 79 个 asmdef 的教训：程序集数量与解耦质量无关，只与 asmdef 维护成本正相关。

### 1.1 AOT / 热更两面（HybridCLR 预留）

| 面 | 程序集 | 内容 | 约束 |
|---|---|---|---|
| AOT | `LiteGame.Core` + `com.litegame.{sim,net,sync}` | 基础设施、宿主壳、判定、协议 | 不出现任何 `LiteGame.Game.*` 类型（含 `using`） |
| 热更候选 | `LiteGame.Game` | 编排、UI、战斗表现、Lua 门面 | 只向下引用；MonoBehaviour 尽量留在场景/AOT 预制体；不重复定义协议结构 |

- 今天**不**创建 `HotUpdate` 程序集、**不**装 HybridCLR、**不**预生成补充元数据（01 §15）。
- 唯一的边界物是 `Core/Boot/{IGame,BootEntry}.cs` + `Game/Boot/GameBootstrap.cs`：AOT 侧只认 `IGame`，业务侧自注册工厂。
- 验收（P0 起每次都查）：`LiteGame.Core` 源码中 `LiteGame.Game` 字样出现 0 次；`LiteGame.Core.asmdef` 的 references 不含 Game。

### 1.2 namespace 约定

| 位置 | namespace |
|---|---|
| `Scripts/Core/Logging` | `LiteGame.Core.Logging` |
| `Scripts/Core/Assets` | `LiteGame.Core.Assets` |
| `Scripts/Game/Boot` | `LiteGame.Boot` |
| `Scripts/Game/Ui` | `LiteGame.Ui` |
| `Scripts/Game/Features/Battle` | `LiteGame.Features.Battle` |
| `Scripts/Editor` | `LiteGame.EditorTools` |

namespace 段数 ≤ 4；目录层级与 namespace 一一对应，不出现 `LiteGame.Game.Modules.Battle.SubModules.Characters` 这类纵深。

## 3. 命名与文件纪律

### 3.1 标识符命名（主流 C#/.NET 规约）

**默认全部遵循 Microsoft C# 命名准则 + Unity 社区通行写法**，不写自有风格。偏离必须登记例外（§3.1.2），未登记 = `verify.py naming` 判红。

| 元素 | 规约 | 正确 | 错误 |
|---|---|---|---|
| 命名空间 | PascalCase，段与目录一致 | `LiteGame.Core.Assets` | `LiteGame.core.assets` |
| 类型（class/struct/record） | PascalCase 名词 | `BattleFeature` | `Battle_Feature`、`BF` |
| 接口 | `I` + PascalCase | `IAssetHost` | `AssetHostInterface` |
| 枚举类型 / 成员 | PascalCase | `AppState.Lobby` | `STATE_LOBBY` |
| 类型参数 | `T` / `T` + PascalCase | `TKey` | `t`、`K` |
| 方法 | PascalCase，动词开头 | `LoadAsync` | `load`、`Load_Data` |
| 异步方法 | 返回 UniTask/Task → `Async` 后缀 | `BuildAsync` | `Build2` |
| 属性 | PascalCase | `IsReady` | `ready` |
| 事件 | PascalCase 过去式 / `Changed` | `RoomJoined`、`RoomListChanged` | `OnRoomJoin`（事件名） |
| 事件处理器 | `On` + 事件名 | `OnRoomJoined` | `RoomJoinedHandler` |
| public 字段 | 优先属性；确需字段用 PascalCase | `PlayerId` | `playerId` |
| private 字段 | `_camelCase` | `_roomClient` | `m_roomClient`、`s_timeout` |
| 局部变量 / 参数 | camelCase | `roomId` | `RoomId` |
| 常量 | PascalCase（.NET 主流，**不用** UPPER_SNAKE） | `MaxRooms` | `MAX_ROOMS` |
| static readonly | PascalCase | `DefaultTimeout` | `s_defaultTimeout` |
| 布尔 | `Is/Has/Can/Should/Needs` 前缀（评审判定） | `IsOwner` | `Owner` |
| 缩写 | ≤2 字母全大写，≥3 字母按单词 | `IO`、`Id`、`Http`、`Ui` | `ID`、`HTTP`、`UI` |
| 禁用 | 匈牙利前缀、`Mgr/Helper/Utils/Common/Tmp/Foo/Bar`、中文标识符、连续下划线 | — | `strName`、`UIMgr` |
| 文件 | = 主类型名，一文件一类型 | `RoomFeature.cs` | `RoomFeatureImpl.cs` |

**Lua**：文件名 `Page_Xxx.lua`，类名同名；方法 PascalCase（`new`/`OnShow`/`OnHide`/`OnReveal`/`OnUpdate`）；字段 `_camelCase`。旧页面已符合，**不新造风格**（03 §9）。

#### 3.1.1 机检边界

`verify.py naming` 用正则检查：命名空间段、类型名、接口名、方法名、字段命名（`_camelCase`/PascalCase）、常量/`static readonly`、异步后缀、文件名 = 首类型名。

**不机检**（正则误报率高）：布尔前缀、局部变量大小写、缩写全大写——归评审。

#### 3.1.2 例外审批（唯一合法偏离通道）

`Tools/naming-exceptions.json`，一条一个对象：

```json
{ "file": "Assets/Scripts/Core/Lua/LuaEnv.cs", "rule": "type", "symbol": "LuaEnv",
  "reason": "xLua 官方类型，源码内必须同名", "approvedBy": "highhunter777", "date": "2026-11-06" }
```

- `file` 支持 `*` 通配；`rule` ∈ `namespace/type/interface/method/field/const/async/file`；`symbol` 可选（精确匹配）。
- **缺 `reason` 或 `approvedBy` 的条目本身判红**——防止"悄悄加白名单"。
- **过期例外判红**：一条都没匹配到违规 = 该例外已无用，删掉。
- 例外只能由用户批准后写入；新增条目即视为一次审批申请。

### 3.2 文件

- **一文件一类型**；文件名 = 类型名（`PageFlow` → `PageFlow.cs`）。例外：Lua 门面的 `Bridge.*` 部分类按语义分文件（§2 已列）。
- 单文件 ≤ 400 行；超过先拆类型，不要拆 partial。
- 单目录 ≤ 20 个 .cs；超过先按职责分目录。
- 生成物目录（`GameData/Generated`、`Scripts/Lua/cfg`）不计入上述预算，但**禁止手改**，文件头必须有生成器标记。

### 3.3 类型后缀语义（唯一含义，不得混用）

| 后缀 | 含义 | 例 |
|---|---|---|
| `Host` | 持有引擎对象/资源，管生命周期 | `AssetHost`、`LuaHost`、`UiHost` |
| `Feature` | 一域/一局的编排者，被 `Game` 持有 | `BattleFeature` |
| `Service` | 无状态业务能力，可被多处以构造参数共享 | `LobbyService`、`SettingsService` |
| `View` | MonoBehaviour 表现件，只读状态、不写逻辑 | `BattleView`、`HudView` |
| `State` | 应用流程态 | `LobbyState` |
| `Api` | 外部协议封装（HTTP/序列化） | `MetaApi` |
| `Catalog` | 静态映射表 | `ScreenCatalog` |
| `Proxy` | 跨边界代理（Lua→C#） | `LuaPageProxy` |
| `Sampler`/`Predictor`/`Reconciler` | 算法件（纯逻辑、可单测） | `InputSampler` |

**禁用名**：`Utils`、`Helpers`、`Common`、`Shared`（作为类型名）、`Manager`（除非它是该域唯一写者，如 `ScreenManager`）、`Base`（仅允许 `ScreenBase` 一个基类）。

### 3.4 目录

- 禁止 `Abstractions/`、`Interfaces/`、`Contracts/` 目录：接口与实现同目录，文件名带 `I` 前缀。
- 禁止 `Modules/`、`SubModules/`：一域一目录，域内平铺 + 语义子目录（`View/`、`Hud/`、`Content/`）。
- 禁止在 `Assets/` 顶层放与 Unity 特殊目录冲突或含义不明的新目录；新增顶层目录必须在本文 §2 登记。

### 3.5 注释

- 类型块注释 ≤ 3 行、成员 ≤ 2 行，写**结论**（这个类型负责什么、有什么非显然约束）。
- 不写：设计理由、历史沿革、批次号、日期、"以前是 X 现在改成 Y"——这些进 `Docs/`。
- 允许：`// 与旧客户端一致：viewFrame 取…` 这类**必须保持兼容的非显然约束**（一行）。
- 中文注释；代码标识符英文。

### 3.6 名字本身：三层命名 + 领域词表

#### 3.6.1 三层分开定，别混用

| 层 | 当前值 | 能否后改 | 判据 |
|---|---|---|---|
| 产品名（游戏标题、对外） | 未定（内部代号 `LiteGameNext`） | **可以**（只改 README/仓库/标题） | 短、可拼读、无版本/技术/尺寸词、与题材相关 |
| 工程与仓库名（文件夹/仓库/解决方案） | `LiteGameNext` | **可以**（GitHub 改名自动重定向） | 与产品名一致，或作为产品名的内部代号 |
| 代码前缀（命名空间/程序集/包） | `LiteGame` | **不可后改**（动全部 `.cs` + asmdef GUID + 资产引用） | 与共享包 `com.litegame.*` 同前缀 |

**结论：产品名与仓库名可以晚定，代码前缀必须现在就锁死。** `LiteGameNext` 里的 `Next` 属于不可治理后缀——它定义的是"下一个"，而"下一个"永远会过期；作为内部代号可以留，作为产品名不合格。

产品名判据（六条）：≤9 字符、可拼读、GitHub/域名/npm 不撞、不含 `Next/Lite/Pro/2/HD` 等版本或尺寸词、能当代码前缀、与题材相关（加分项）。

#### 3.6.2 领域词表（一个概念一个词，C# 与 Lua 共用）

| 词 | 含义 | 禁用同义词 | 边界 |
|---|---|---|---|
| `Boot` | 进程启动态 | Startup、Init | 只指 `AppState.Boot` |
| `Patch` | 内容补丁 | Update | `Update` 只出现在 Unity 回调，不做名词 |
| `Login` | 登录态 | Auth | `Auth` 留给协议/第三方 |
| `Lobby` | 登录后大厅（房间列表/创房/战绩） | Hall | 只有列表与入口，没有席位 |
| `Room` | 一个房间（席位/房主/开局） | Session | `Session` 是协议内部词，不进领域层 |
| `Battle` | 一局对战（`StartGame`→`MatchEnded`） | Match、Fight | **协议词用 `Match`，客户端领域词用 `Battle`**，不复用 |
| `Result` | 结算态 | Settlement | `Settlement` 仅当引用协议字段时出现 |
| `Screen` | 一个 UI 页面（C#：`ScreenId`/`ScreenBase`） | Form、View | `View` 只指 3D 表现件 |
| `Page` | Lua 侧页面（`UI.Page_Lobby`） | Form | `Screen` ↔ `Page` 一一对应 |
| `Feature` | 一域编排（Meta/Battle/Settings） | Module | `Module` 整体禁用 |
| `Service` | 无状态能力 | Helper | — |
| `Host` | 持引擎对象/资源 | Manager | `Manager` 仅 `ScreenManager` |
| `Player` | 席位（协议 `PlayerId`） | User | — |
| `Character` | 场景实体表现 | Avatar | — |
| `Map` | 玩法地图（表行 / `MapId`） | Level | `Level` 留给 Unity 场景 |
| `Scene` | Unity 场景文件 | Map | 与 `Map` 严格分开 |
| `Config` | 配置装载与摘要 | Settings | `Settings` = 用户偏好 |
| `Content` | 可热更内容（Lua/配置/包） | Asset | `Asset` = 单个资源 |
| `Signal` | Core 的强类型通知 | Event | 禁 `EventBus` |

规则：**一个概念只用一个词**；同义词只允许出现在"引用协议字段/第三方 API"的场合，并在注释里标明来源。

## 4. 资源与场景

### 4.1 场景（2 个）

## 6. 与旧仓的共享输入（迁移期最重要的机制）

新客户端依赖旧仓的**四类共享输入**，任何一类漂移都会导致"能编过、联机分叉"：

| 共享输入 | 旧仓位置 | 新工程落点 | 同步方式 |
|---|---|---|---|
| 共享包 `sim/net/sync` | `Test/Packages/com.litegame.*` | 同名包目录 | **引用不拷贝**（§6.1） |
| 配置表 C# 生成物 | `Test/Assets/GameData/Generated` | `Assets/GameData/Generated` | `sync_shared.py`（哈希校验） |
| 配置表数据 + Lua 表 | 旧仓 Luban 输出 | `Assets/GameData/Config`、`Assets/Scripts/Lua/cfg` | `gen_config.py` 直生成（单源表） |
| BuildHash 常量 | 包内 `Core/Protocol/BuildHash.g.cs` | 随包 | 只读，禁改 |

### 6.1 决策：迁移期用 `file:` 引用，切换期改快照

```jsonc
// Packages/manifest.json（迁移期）
"com.litegame.sim":  "file:../Test/Packages/com.litegame.sim",
"com.litegame.net":  "file:../Test/Packages/com.litegame.net",
"com.litegame.sync": "file:../Test/Packages/com.litegame.sync"
```

| 方案 | 优点 | 缺点 | 何时用 |
|---|---|---|---|
| **A. `file:` 引用旧仓**（推荐） | 旧仓改协议/判定，新客户端自动跟随；BuildHash 天然一致 | 路径依赖（换机需保持同级目录）；旧仓重构目录会断 | 迁移期（P0–P3） |
| B. 拷贝快照 | 自包含、可独立归档 | 两份源，协议一改就分叉；必须靠脚本同步 | 切换期（P4 之后） |

**切换条件**：旧仓不再有客户端改动、且服务端协议冻结一个版本 → 拷贝快照并在本文登记新路径。

### 6.2 生成物同步（`Tools/sync_shared.py`）

- 从旧仓复制：`Assets/GameData/Generated/**`、`Luban` 输出的 Lua 表。
- 复制后写 `Assets/GameData/.synced.json`：每个文件的 `sha256` + 旧仓 HEAD 短号。
- `verify.py --shared` 对比哈希：不一致即失败并打印"旧仓已重生成，请跑 sync_shared.py"（无 `.synced.json` 时跳过）。
- 这条机制替代旧仓的 buildhash 多目标脚本在本工程内的部分职责；**共享源码哈希仍以包内常量为准**。

### 6.3 xUnit 工程如何测 Unity 侧纯逻辑

`Tests/LiteGame.Tests.csproj` 不引用 Unity DLL，而是用 `<Compile Include="..\Assets\Scripts\Core\**\*.cs" Link="...">` 链接**不依赖 UnityEngine 的文件**（`ConfigDigest`、`LocalPredictor`、`InputSampler`、`Wire/*`）。

约束（否则链不进来）：这些文件**不得** `using UnityEngine`；需要引擎能力的部分拆成 `Xxx.Host.cs`（留在 Unity 侧）与 `Xxx.cs`（纯逻辑）。这是让"判定对拍"能在 CI 秒级跑通的关键，也是 01 R4 里"测试替身"接口的最主要用途。
